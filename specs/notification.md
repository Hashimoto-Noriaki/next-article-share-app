# 通知機能 E2Eテスト計画

## Application Overview

テックブログ共有アプリのヘッダーにある通知ベル（NotificationBell）を対象としたE2Eテスト計画。他ユーザーが自分の記事にいいね／コメントすると通知が作られ、ベルに未読数バッジが表示される。ベルをクリックするとドロップダウン（見出し「通知」、未読があれば「全て既読にする」ボタン、0件なら「通知はありません」）が開き、通知アイテムをクリックすると既読化されて記事詳細へ遷移する。自分自身の操作では通知は作られない。記事の投稿、いいね・コメント機能そのもの、認証自体は対象外とし、通知の発生・表示・既読化のみを検証する。UI構成と挙動は実ブラウザ（localhost:3000）で探索して確認済み。

各シナリオはseedのログイン状態を引き継がず、createTestUser()/signup()で自分でログイン状態を作る。送る人（送信者）と受け取る人（受信者）は browser.newContext() で分け、ユーザー名は createTestUser('受信者') / createTestUser('送信者') のように区別する。ログアウトは使わない（ログアウト直後にセッションが復活する不具合 #485 があるため）。受信者は新規ユーザーなので、通知は各シナリオで自分が起こした操作の分だけになる前提で書いてよい。

## 探索で確認した実挙動と推奨ロケーター

- ベルボタン: `page.getByRole('button', { name: '通知' })`。aria-label="通知" が付いているため、未読バッジ（数字）が中にあってもアクセシブル名は常に「通知」のまま。ヘッダーにベルは1つだけ（記事一覧・記事詳細どちらでも同じ）なので strict mode 違反にならない。
- 未読数バッジ: ベルボタン内の `<span>`（赤丸）で、専用のロールや data-testid はない。件数の確認は `bell.toHaveText('2')` または `toContainText('2')`、バッジが無いことの確認は `bell.toHaveText('')`（ボタン内はアイコンのみ）で行う。10件以上は「9+」表示。
- バッジの表示タイミング（重要）: 通知一覧は TanStack Query で「ページ読み込み時（ベルのマウント時）」と「ベルを開く（クリックする）とき」に取得される。ポーリング（refetchInterval）は無く、staleTime は1分、ウィンドウフォーカス時の再取得も staleTime 内は走らない。したがって、受信者のページを開いたまま送信者が操作しても、受信者側のバッジは自動では更新されない。ベルを開くか、ページ遷移／リロードで初めて更新される。送信者の操作を先に済ませてから受信者側でページを開けば、リロードなしでバッジは表示される。ただし取得は読み込み後の非同期処理なので、バッジは一瞬遅れて出る（0件のスナップショット直後に出る場合があるため、expect の自動リトライで待つこと。固定 sleep は使わない）。なお「開いたままの受信者ページで送信者の操作後に未読数が変わらない」点は、単一タブでの探索では同時操作を再現できなかったためコード（useNotifications.ts）から確認した内容である。テスト化する場合は 1.3 の補足を参照。
- テストの書き方の推奨: 受信者が記事を公開 → 送信者が別コンテキストでいいね／コメント → 送信者のコンテキストを閉じる → 受信者の page で `page.goto('/articles')`（またはリロード）してバッジを `expect` で待つ、の順にする。受信者の page を送信者の操作の前に開いたままにする場合は、操作後に必ず goto/reload するか、ベルを開いて再取得させる。
- ドロップダウン（ベルをクリックで開く）: 見出し `page.getByRole('heading', { name: '通知', level: 3 })`。未読があるときだけ `page.getByRole('button', { name: '全て既読にする' })` が表示される。0件のときは `page.getByText('通知はありません')`。ドロップダウンにはロール（menu 等）がない。外側クリックや再度ベルクリックで閉じる（useDropdown）。
- 通知アイテム: `<a>`（role=link）で、アクセシブル名は「送 送信者さんがあなたの記事にいいねしました たった今」のようにアバター文字・メッセージ・相対時刻が連結される。推奨ロケーターは `page.getByRole('link', { name: '送信者さんがあなたの記事にいいねしました' })`（部分一致）。href は `/articles/{記事ID}`。メッセージは「{送信者名}さんがあなたの記事にいいねしました」「{送信者名}さんがあなたの記事にコメントしました」。相対時刻は「たった今」。
- 並び順: 新しい通知が上（今回の探索ではコメント通知がいいね通知より上）。順序に依存する検証は避け、リンクの name で特定する。
- 未読のスタイル: 未読アイテムのクラスに bg-cyan-50 が付く。ロール等では判別できないため `toHaveClass(/bg-cyan-50/)`（既読は `not.toHaveClass(/bg-cyan-50/)`）を使う。
- 1件ずつ既読: 未読の通知アイテムをクリックすると、既読化（サーバー反映）とドロップダウンのクローズが起き、記事詳細（`/articles/{記事ID}`）へ遷移する。探索では2件の未読があるとき1件クリック後、遷移先ページのバッジが「2」から「1」になった。再度ベルを開くと、クリックした通知は bg-cyan-50 が外れ、未クリックの通知は付いたまま（既読状態は再取得後も保持される）。「全て既読にする」ボタンは未読が残る間は表示され続ける。
- まとめて既読: 「全て既読にする」をクリックするとバッジが消え、「全て既読にする」ボタン自体も消える。ドロップダウンは開いたままで、通知一覧は残る（既読になり bg-cyan-50 が外れる）。
- 自分の操作: 自分の記事に自分でコメントしても通知は作られない。探索では、コメント投稿後にベルを開いても通知件数は増えず、バッジも出なかった。
- 0件: 新規ユーザーがベルを開くと見出し「通知」と「通知はありません」のみが表示され、「全て既読にする」は表示されない。
- 送信者のいいね: 記事詳細のいいねボタン（アクセシブル名が数字のみ）`page.getByRole('button', { name: /^\d+$/ })` をクリックし、`toHaveText('1')` で反映を待つ。コメントの投稿は e2e/comment.spec.ts の postComment と同様（プレースホルダー「コメントを入力...」に入力して「コメントする」をクリック、本文が表示されるまで待つ）。いずれも送信者のコンテキストを閉じる前に完了を待つこと。
- 探索環境の注意: 探索では seed の signup が一度タイムアウトした（dev サーバー初回コンパイルが原因と思われる）。再実行で成功した。本番のテストでは signup のタイムアウト（10秒）が初回に不足する場合があるので、失敗時は再実行で確認する。

## Test Scenarios

すべてのシナリオを `e2e/notification.spec.ts` にまとめる。

### 1. 通知機能

**Seed:** `e2e/seed.spec.ts`

#### 1.1. 他ユーザーのいいねで通知が届き、ベルに未読数が出る

**File:** `e2e/notification.spec.ts`

**Steps:**

1. テストの page で createTestUser('受信者') を作成し、signup() で新規登録・ログインする
2. createTestArticle() でテスト記事データを作成し、createArticle() で記事を公開する
3. browser.newContext() で送信者用のコンテキストとページを作る
4. 送信者用ページで createTestUser('送信者') を作成し、signup() で新規登録・ログインする
5. 送信者用ページで navigateToArticle() し、いいねボタン（`getByRole('button', { name: /^\d+$/ })`）をクリックして `toHaveText('1')` になるまで待つ
6. 送信者用のコンテキストを閉じる
7. 受信者の page で `page.goto('/articles')` を行う（リロード相当。この時点で初めて通知を取得させる）
8. ベルボタン（`getByRole('button', { name: '通知' })`）に未読数バッジ「1」が表示されるのを待つ
9. ベルボタンをクリックしてドロップダウンを開く

**Expected Results:**

- 手順8でバッジが「1」になる（`expect(bell).toHaveText('1')`。自動リトライで待つ）
- ドロップダウンに見出し「通知」と「全て既読にする」ボタンが表示される
- 「送信者さんがあなたの記事にいいねしました」のリンクが1件表示され、href が `/articles/` で始まる記事詳細へのリンクである
- そのアイテムは未読スタイル（bg-cyan-50）を持つ
- 「通知はありません」は表示されない

#### 1.2. 他ユーザーのコメントで通知が届く

**File:** `e2e/notification.spec.ts`

**Steps:**

1. テストの page で createTestUser('受信者') + signup() でログインし、createTestArticle() + createArticle() で記事を公開する
2. browser.newContext() で送信者用のコンテキストとページを作り、createTestUser('送信者') + signup() でログインする
3. 送信者用ページで navigateToArticle() し、ユニークなコメント本文（`通知テストコメント ${Date.now()}`）を投稿して本文が表示されるまで待つ
4. 送信者用のコンテキストを閉じる
5. 受信者の page で `page.goto('/articles')` を行い、ベルボタンのバッジが「1」になるのを待つ
6. ベルボタンをクリックしてドロップダウンを開く

**Expected Results:**

- バッジが「1」になる
- 「送信者さんがあなたの記事にコメントしました」のリンクが1件表示され、未読スタイル（bg-cyan-50）を持つ
- 通知メッセージにコメント本文は含まれない（メッセージは固定文言）
- 「送信者さんがあなたの記事にいいねしました」は表示されない（コメントのみのため）

#### 1.3. 通知一覧を開ける（0件のとき「通知はありません」）

**File:** `e2e/notification.spec.ts`

**Steps:**

1. テストの page で createTestUser('受信者') + signup() で新規登録・ログインする（記事の作成やほかユーザーの操作は行わない）
2. ヘッダーのベルボタンにバッジが表示されていないことを確認する（`toHaveText('')`）
3. ベルボタンをクリックしてドロップダウンを開く
4. 見出し「通知」（level 3）と「通知はありません」が表示されていることを確認する
5. 再度ベルボタンをクリックしてドロップダウンを閉じる

**Expected Results:**

- 新規ユーザーはバッジが表示されない
- ドロップダウンに見出し「通知」と「通知はありません」が表示される
- 「全て既読にする」ボタンは表示されない
- 通知アイテム（`getByRole('link', { name: /さんがあなたの記事に/ })`）が存在しない（toHaveCount(0)）
- ベルの再クリックでドロップダウン（見出し「通知」）が閉じる

**補足（任意の追加シナリオ）:** 開いたままの受信者ページで、送信者の操作後にベルを開くと未読数が更新されることを確認する場合は、受信者の page で `/articles` を開いてバッジが無いことを確認 → 送信者用コンテキストでいいね → 受信者の page で（リロードせずに）ベルをクリック → ドロップダウン内に通知アイテムが表示され、バッジが「1」になる、という流れになる。送信者操作の直後に受信者側のバッジが自動更新されないことを「消極的に」検証するのは、staleTime とタイミングに依存して不安定になりやすいため、必須シナリオには含めない。

#### 1.4. 通知を1件ずつ既読にできる（クリックで記事詳細へ遷移し未読数が減る）

**File:** `e2e/notification.spec.ts`

**Steps:**

1. テストの page で createTestUser('受信者') + signup() でログインし、createTestArticle() + createArticle() で記事を公開する
2. browser.newContext() で送信者用のコンテキストとページを作り、createTestUser('送信者') + signup() でログインする
3. 送信者用ページで navigateToArticle() し、いいねをクリックして `toHaveText('1')` を待った後、ユニークなコメント本文を投稿して本文が表示されるまで待つ（通知が2件になる）
4. 送信者用のコンテキストを閉じる
5. 受信者の page で `page.goto('/articles')` を行い、ベルボタンのバッジが「2」になるのを待つ
6. ベルボタンをクリックしてドロップダウンを開き、2件とも未読スタイル（bg-cyan-50）であることを確認する
7. 「送信者さんがあなたの記事にいいねしました」のリンクをクリックする
8. 遷移先の URL と、ベルのバッジを確認する
9. ベルボタンを再度クリックして開き、各通知の未読スタイルと「全て既読にする」ボタンの有無を確認する

**Expected Results:**

- 手順7のクリックで記事詳細ページ（`/articles/{記事ID}`、`toHaveURL(/\/articles\/[^/]+$/)`）へ遷移し、記事タイトルが表示される
- クリック直後にドロップダウンが閉じている（見出し「通知」の level 3 が表示されていない）
- 遷移後のベルのバッジが「1」に減っている（`toHaveText('1')`）
- 再度ベルを開くと、クリックした「いいね」の通知は bg-cyan-50 を持たず（既読）、「コメント」の通知は bg-cyan-50 を持つ（未読）
- 未読が1件残っているため「全て既読にする」ボタンは表示されている
- 既読化はサーバーに反映されており、再取得（ベルを開くたびに実行される）の後も既読のまま

#### 1.5. 通知をまとめて既読にできる

**File:** `e2e/notification.spec.ts`

**Steps:**

1. 1.4 の手順1〜5と同じく、受信者が記事を公開し、送信者がいいねとコメントを行い、受信者の page でバッジが「2」になるところまで進める
2. ベルボタンをクリックしてドロップダウンを開く
3. 「全て既読にする」ボタンをクリックする
4. ページをリロードするなどして再取得させ、状態が保持されているか確認する（`page.reload()` 後に再度ベルを開く）

**Expected Results:**

- クリック後、ベルのバッジが消える（`toHaveText('')`）
- 「全て既読にする」ボタンが消える（`toHaveCount(0)`）
- ドロップダウンは開いたままで、通知2件はリストに残っており、いずれも bg-cyan-50 を持たない
- リロード後もバッジは表示されず、再度ベルを開いても「全て既読にする」ボタンは表示されず、2件とも既読スタイルのまま

#### 1.6. 自分の記事への自分のコメントでは通知が作られない

**File:** `e2e/notification.spec.ts`

**Steps:**

1. テストの page で createTestUser('受信者') + signup() でログインし、createTestArticle() + createArticle() で記事を公開する
2. navigateToArticle() で自分の記事の詳細ページへ遷移する
3. ユニークなコメント本文（`自分のコメント ${Date.now()}`）を投稿し、本文が表示されるまで待つ
4. ベルボタンをクリックしてドロップダウンを開く（ベルを開くと通知が再取得される）
5. `page.reload()` し、再度ベルにバッジが出ていないことを確認する

**Expected Results:**

- ベルボタンにバッジが表示されない（`toHaveText('')`）
- ドロップダウンに「通知はありません」が表示される
- 通知アイテム（`getByRole('link', { name: /さんがあなたの記事に/ })`）が存在しない（toHaveCount(0)）
- 自分自身のコメントは通知の対象外である
